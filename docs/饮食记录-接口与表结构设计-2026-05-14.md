# 饮食记录模块接口与表结构设计

## 1. 设计目标

基于猫咪详情页新增【饮食记录】页签，第一版重点支持：

1. 当前喂养方案
2. 每日喂食记录
3. 换粮计划
4. 补剂/保健品疗程
5. 顶部摘要概览

设计原则：

1. 尽量贴合现有 FastAPI + SQLite + 单页详情页结构。
2. 支持 MVP 直接落地，也为后续提醒/统计预留空间。
3. 降低录入成本，热量等高级字段允许为空。

## 2. 数据表设计

### 2.1 `feeding_plans`

用于记录“当前或历史喂养方案”。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INTEGER PK | 主键 |
| `cat_id` | INTEGER FK | 猫咪 ID |
| `name` | VARCHAR | 方案名 |
| `start_date` | DATE | 生效日期 |
| `end_date` | DATE NULL | 结束日期 |
| `food_type` | VARCHAR | 干粮/湿粮/混喂/冻干/处方粮 |
| `brand` | VARCHAR NULL | 品牌 |
| `product_name` | VARCHAR | 产品名 |
| `life_stage` | VARCHAR NULL | 幼猫/成猫/老年/全阶段/处方 |
| `complete_balance_status` | VARCHAR | `yes/no/pending` |
| `daily_amount` | FLOAT NULL | 每日计划量 |
| `amount_unit` | VARCHAR NULL | `g/can/bag/ml` 等 |
| `feeding_frequency` | VARCHAR NULL | 每日几次 |
| `daily_calories` | FLOAT NULL | 每日目标热量 |
| `hydration_strategy` | VARCHAR NULL | 饮水辅助方式 |
| `notes` | TEXT NULL | 备注 |
| `is_active` | BOOLEAN | 是否当前生效 |
| `created_at` | DATETIME | 创建时间 |
| `updated_at` | DATETIME | 更新时间 |

## 3. API 设计

### 3.1 概览

#### `GET /api/cats/{cat_id}/feeding/overview`

返回：

1. 当前生效喂养方案
2. 当前换粮计划
3. 当前生效补剂疗程
4. 今日喂食记录
5. 最近异常记录
6. 今日计数摘要

返回示例：

```json
{
  "active_plan": {},
  "active_transition_plan": {},
  "active_supplement_courses": [],
  "today_records": [],
  "recent_reactions": [],
  "daily_summary": {
    "main_food_count": 2,
    "canned_food_count": 1,
    "treat_count": 1,
    "supplement_count": 2,
    "refused_count": 0
  }
}
```

### 3.2 喂养方案

#### `GET /api/cats/{cat_id}/feeding/plans`

获取该猫全部喂养方案，按“当前生效优先、时间倒序”返回。

#### `POST /api/cats/{cat_id}/feeding/plans`

创建喂养方案。

如果 `is_active = true`，自动将同猫其他方案置为非当前。

#### `PUT /api/feeding/plans/{plan_id}`

更新喂养方案。

#### `DELETE /api/feeding/plans/{plan_id}`

删除喂养方案。

### 3.3 喂食记录

#### `GET /api/cats/{cat_id}/feeding/records`

获取该猫全部喂食流水，按时间倒序。

#### `POST /api/cats/{cat_id}/feeding/records`

创建一条喂食记录。

#### `PUT /api/feeding/records/{record_id}`

更新一条喂食记录。

#### `DELETE /api/feeding/records/{record_id}`

删除一条喂食记录。

### 3.4 换粮计划

#### `GET /api/cats/{cat_id}/feeding/transitions`

获取换粮计划列表，携带 `steps`。

#### `POST /api/cats/{cat_id}/feeding/transitions`

创建换粮计划。

如果调用方没传 `steps`，后端自动按 `planned_days` 生成默认模板。

#### `PUT /api/feeding/transitions/{transition_id}`

更新换粮计划，并允许整体替换步进。

#### `DELETE /api/feeding/transitions/{transition_id}`

删除换粮计划。

### 3.5 补剂疗程

#### `GET /api/cats/{cat_id}/feeding/supplements`

获取补剂/保健品疗程列表。

#### `POST /api/cats/{cat_id}/feeding/supplements`

创建补剂疗程。

#### `PUT /api/feeding/supplements/{course_id}`

更新补剂疗程。

#### `DELETE /api/feeding/supplements/{course_id}`

删除补剂疗程。

## 4. 前端组件设计

第一版采用独立组件：

- `frontend/src/components/CatFeedingTab.vue`

挂载位置：

- `frontend/src/views/CatDetail.vue`

页签结构：

1. 摘要卡
2. 当前喂养方案
3. 每日喂食记录
4. 换粮计划
5. 补剂疗程

这样比直接继续堆进 `CatDetail.vue` 更易扩展。

---

## 5. MVP 范围说明

第一版已刻意收敛，不做：

1. 精准热量预算和热量进度条
2. 自动提醒服务
3. 饮食与体重的自动关联分析
4. 多猫饮食横向统计

但表结构已经为这些能力预留了基础字段和关联关系。

## 6. 自动化测试建议

建议同时保留三层脚本：

1. 后端单元/接口测试：`pytest + TestClient`
2. 前端基础构建校验：`vite build`
3. UI 自动化脚本：Playwright CLI 或脚本化浏览器检查

本轮开发会按这个方向一并落地。
